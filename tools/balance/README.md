# tools/balance: balance harness runner (NX-031 part 1)

Headless runs of the real sim with scripted viewers, for the six crowd profiles, with a report per run and per profile.
Spec: Q-SIM-91 (OPEN-QUESTIONS), TESTING-STRATEGY §3.5 and §3.5a (A1 to A6), Q-TEST-2 and Q-TEST-4 to Q-TEST-8, Q-ALN-42.
This is part 1. Part 2 (adversarial profiles, A5 and A6, NX-321) and part 3 (the nightly 20-seed diff job and trend chart, a CI change) are not here.

```
cd services/sim && uv run --frozen python ../../tools/balance/balance.py \
    --profile prime-50 --seeds 5 --hours 72 --workers 4 --out /path/to/new-report-dir
```

| Flag | Meaning |
|---|---|
| `--profile` | one of `overnight-0`, `quiet-5`, `prime-50`, `evening-150`, `raid-300`, `surge-500`, or the check profile `freelance-50` (below); a comma list; or `all` (default: the six standard profiles, never `freelance-50`) |
| `--seeds` | a count N (seeds 1..N) or a comma list; the sim seed is the seed itself |
| `--hours` | game hours per run, default `campaign.time_limit_h` of the config in use (72 shipped, the acceptance length; follows `--set campaign.time_limit_h=...`). A run stops early when the campaign ends. Short runs work; targets that need a longer window say `not evaluable` |
| `--workers` | parallel processes, one run each (default 1). `run_jobs` submits the runs biggest crowd first (`viewers` from `profiles.yaml`; ties keep the order given; the README's measured seconds per game hour rise with it: prime-50 31, evening-150 65, raid-300 150, surge-500 225), and a worker that finishes takes the next waiting run at once (backfill, no fixed chunks). Results go back to job order before the report is built, so the report does not depend on workers or completion order (NX-432). Across queued issues the queue overlaps jobs on one worker budget: see "Overlapping jobs (NX-442)" under Local run queue |
| `--set` | `key=value`, repeatable: override one numeric or boolean key of the shipped balance config (dotted path, e.g. `tasking.strike_idle_targets_max=0`, `economy.legacy_rules=false`, `economy.unlimited.ENEMY=false`). A boolean key takes `true` or `false` only (lower case); a numeric key a number only, never a boolean (NX-412 part 5a). An unknown key, a section, a value of the wrong type, a float for an integer key, a key given twice or a value the schema rejects exits 2 before any run. The overridden copy is saved as `<out>/balance.yaml`, every worker loads it, and the report header lists the overrides next to the (changed) config hash, plus the economy mode (below) |
| `--theater` | a theater file to run on instead of `content/theaters/strait-1.yaml`. Loaded with the sim's own loader (and cross-checked with the balance config) before any run: a missing, malformed or inconsistent file exits 2 with one stderr line, before `--out` exists. The loader wants the slug to equal the file name, so the copy is saved as `<out>/theater/<file name>` (not a fixed `theater.yaml`; a subdirectory so a file named `balance.yaml` cannot clobber the `--set` copy), every worker loads that copy, and the report header shows its slug, name, node count, landing-base count and the config hash (the theater is part of `config_hash`). The queue has no theater key on purpose: a hostile issue naming files on the owner's PC is a security surface, so adding one is a separate owner decision |
| `--out` | report directory; must not exist (unless `--resume`) |
| `--slot-dir DIR`, `--slot-key N` | (NX-460; both or neither, else exit 2; `N` a non-negative integer, the queue passes the issue number; `DIR` must hold `slot-*` files) share a host-wide pool of slot files with other jobs, so a job widens when another ends. Before each run a worker takes one `DIR/slot-*` with an exclusive `flock` (lowest free first, retrying every 2 s) and closes it when the run ends; the kernel frees it if the process dies. While a worker waits it holds a shared lock on `DIR/wait-<N, 9 digits>`, and it takes no slot while a job with a smaller key has a waiting worker (oldest job first; a killed job's lock frees itself, so a stale file blocks no one; `balance.py` never deletes wait files, the queue clears the unlocked ones at tick start). The seconds a run waited are `timing.slot_wait_s` in its JSON (`wall_s` excludes them); the report's `timing.slot_wait_s` is their sum and `report.md` has a `slot wait` line (runs saved before NX-460, kept by a resume, count 0). Absent: no slot code runs and `slot_wait_s` is 0.0. Put `DIR` on the Linux file system, not on `/mnt/c` |
| `--resume` | continue a killed job in an existing `--out` (NX-433): keep each `runs/<profile>-s<seed>.json` that parses and matches profile, seed, hours and config hash, rerun the rest, build the report from all. The check does not see an edit to `profiles.yaml` between attempts (the report header's `profiles_digest` would then reflect the new file while kept runs used the old); the queue always resumes at the same sha, so it cannot happen there |

Output: `report.md` and `report.json` (config hash, profiles.yaml digest, seeds, hours, wall times, the target table, per-profile aggregates, one headline row per run), `runs/<profile>-s<seed>.json` (the full per-run report: metrics, momentum curve at one sample per game minute, command and response counts, final `state_hash`, timing) and `logs/<profile>-s<seed>/` (the run's command log). While a run goes, `runs/<profile>-s<seed>.progress` holds one line, `<tick> <total_ticks> <unix time>`, rewritten (`.tmp`, then renamed) at most once a minute (the clock is read every 600 ticks) and removed once the result JSON is written; a resume ignores and overwrites it, and the queue counts `runs/*.json` only, so it is never taken for a result. Wall time, slot wait and ticks per second are the only values that differ between two runs of the same seed; they sit under `timing` (and `wall_s` and `ticks_per_s` in the run rows).

## How a run works

`runner.run` builds the campaign with `start_campaign` from the shipped config (the path the goldens use), then each tick: the viewers whose wake-up is due send commands, the commands are appended to a command log (the NX-103 format `tools/replay` reads, written before the tick that applies them), and `step(world, commands, HANDLERS)` runs with the production handler registry. Events feed the metrics and the viewers (a spawn, a queue place, a rejection, a loss). `runner.replay_log` rebuilds a run from its log alone and reaches the same final `state_hash` (tested). `tools/replay/replay.py` needs a snapshot directory, which the harness does not write yet.

The harness has its own seeded `random.Random` streams (the arrival schedule per profile and seed, and one per viewer), never the sim's. Commander ids are synthetic, deterministic UUIDv7-shaped ids; `SYS_SET_CALLSIGN` is not used because JOIN does not need a callsign.

## Profiles and personas: `profiles.yaml`

Only the six profile names and sizes are decided (Q-ALN-42, Q-TEST-5). **Every other value in `profiles.yaml` is PROPOSED**: the ramp length, the arrival rate after the ramp, each profile's persona mix, and each persona's behaviour (join, rejoin and rebase chances and delays). No spec gives them. They are harness inputs, not game balance, and are re-tuned once the first runs show what a believable crowd looks like. The report carries the file's digest so runs compare only on the same crowd.

**A profile name is the number of distinct viewers who arrive in the ramp, not the concurrent count.** Viewers who lose their unit and do not come back leave, and later arrivals join, so the peak with a live unit at once differs; every run reports `viewers.peak_concurrent` (most viewers holding a unit at once) beside `viewers.distinct`.

A profile has `viewers` distinct viewers arriving at uniform seeded times in the first `ramp_min` minutes, then new distinct viewers at `arrivals_per_hour` (Poisson, seeded) for the rest of the run. A viewer leaves only by losing its unit and not re-joining (there is no leave command yet, Q-SIM-91).

| Persona | Behaviour (commands that exist: JOIN with a role and no target or `hold`, and REBASE) |
|---|---|
| lurker | rarely joins (a role of any kind); rarely comes back |
| newbie | a bare join as STRIKE (a role is required by the contract; no target, so the board auto-tasks it); usually comes back |
| veteran | joins STRIKE; nearly always comes back. Its one REBASE to the most forward friendly airbase is built but **off** (`rebase_prob` 0): an accepted REBASE sets HOLD and nothing clears it until the parser's unit orders exist (NX-192), so rebased units would park for good. Turn it back on (0.5) then |
| logistics-lover | joins LOGI; nearly always comes back |
| afk-farmer | joins STRIKE with `hold`, then does nothing and never comes back |

### A1 steamroll check (NX-411, Q-TEST-11)

Only a campaign that ended in VICTORY is judged; a lost, time-limit or unfinished one shows "not judged". All thresholds are `targets.steamroll_*` in `profiles.yaml` and **PROPOSED** (Q-TEST-11), recalibrated once a hard-fought run exists. A signal that cannot be measured has no value, does not fire and says why (`note` in `report.json`; `n/m` in the table).

| Signal | Value, from | Fires when |
|---|---|---|
| S1 Static pressure on held ground | pressure events per 4 campaign hours (events x 4 / `length_h`). A pressure event is a `CaptureStarted` by the Static on a node the coalition holds, a `NodeDefensesDown` with owner COALITION, or a `NodeCaptured` that takes a node from the coalition (any node kind, not only strategic). Ownership starts from the setup and follows `NodeCaptured` | under `steamroll_pressure_per_4h` (2) |
| S2 contested final hold | pressure events at or after the start of the last victory-hold run, and the holds broken before it. The run comes from the sim's `VictoryHoldStarted` / `VictoryHoldBroken` (ECONOMY EC-9, NX-412 part 5a; before, the harness derived the same rule from `NodeCaptured`): the coalition owning at least `campaign.victory_node_frac` of the strategic nodes; a dip closes a run (a broken hold) and the campaign ends in VICTORY when the run lasts `victory_hold_min`. A win by HQ capture while below the fraction has no hold: S2 is "not measurable" and does not fire | both are 0 |
| S3 momentum swing | the existing momentum samples (one per game minute). The coalition leads above `steamroll_lead_line` (50), the Static below it. Largest drop from the running peak after the first coalition lead; lead changes count each flip of the leader after the first leader is set (a start below 50 then a first lead is 1 change). Never led: not measurable | drop under `steamroll_swing_pts` (10) and at most `steamroll_max_lead_changes` (1) changes |
| S4 late Static force | per-minute samples (`Collector.sample`): the Static's live armed units that are not Disabled, and the stock of the finite-stock bases it owns. In the last third of the campaign (by `end_tick`): the mean of each against the run's own peak units and the stock at tick 0 | units under `steamroll_late_units_frac` (25%) of peak, or stock under `steamroll_late_stock_frac` (10%) of start |

- An HQ-capture win while at or above the victory fraction judges S2 on the short, incomplete last hold.
- S3 counts lead changes over the whole campaign but measures the drop only after the first coalition lead.
- S4's late stock counts only the bases the Static owns at that time, so losing bases lowers it (intended: a beaten Static).
- S4 uses the mean over the late third, not the last sample.
- The A1 steamroll share is information only until a threshold is decided (Q-TEST-12).

Steamroll = S1 and S2 both fire, or at least `steamroll_min_signals` (3) of S1 to S4 fire. The report has a per-seed table (each value, `*` when it fired) and the share of won seeds flagged per profile (also `A1.steamroll` in `report.json`).

### A2 and impact (NX-383, Q-SIM-93)

**Which newbies.** A2 judges only newbies whose first JOIN finds the Static Director's tier (`world.director["ENEMY"].tier`, as `tasking_gen._idle_targets_open` reads it) at `targets.a2_min_tier` (ALPHA) or above. At Pattern of Life the board posts no strike work by design (Q-SIM-85, Q-SIM-92). Those arrivals are counted (`joined_below_tier`, their times in `below_tier_ttfi_s`) and shown as "information only"; the report names both counts and never judges the second.

**What is an impact.** Any real contribution; the first of these by the newbie's unit sets its time:

| Kind | Source |
|---|---|
| `hit` | `WeaponImpact` with `hit` true, shooter owned by the newbie |
| `kill` | `UnitDestroyed` of an enemy, the newbie's unit the killer |
| `delivery` | `SupplyDelivered` with the newbie's commander id |
| `capture` | `NodeCaptured` naming the newbie a participant; or, derived from world state every `impact_check_s`, a GROUND unit of the newbie inside `capture.radius_m` of a node whose capture bar the coalition fills (no `CaptureProgress` event is emitted, and `CaptureStarted` names no commander) |
| `departure` | derived from world state every tick (`Collector.observe`, so the tick is exact): the first tick a newbie's own truck (a `supply.carriers` kind) holds cargo and a path, i.e. it loaded at its source and set off for a delivery. No event names the load. A truck that spawns or sets off empty (a capture run, a bare JOIN waiting for work) does not count; its later `delivery` does. Applies to every persona kind |
| `scout` | derived from world state every `impact_check_s`: a coalition track not seen before, within the newbie's recon unit's sensor reach (radius x the target's stealth). No event says who tracked what, and masking is not applied, so this is an approximation |

When two kinds land in the same tick the earlier row of `metrics.IMPACT_KINDS` (kill, capture, delivery, departure, scout, hit) is recorded. `scout` is the first coalition track never seen before that falls inside the sensor reach of a recon (painter) unit of the newbie's own.

**A2 rule (Q-SIM-97).** Pass needs both. (1) The median time to first impact is at most `targets.a2_max_s` (480 s). A newbie with no impact after being watched `a2_max_s` or longer counts as a miss (infinite); one watched for less when the run ended is unresolved and left out. (2) The tail share is at most `targets.a2_tail_share` (10%): of the newbies whose fate is known past `targets.a2_tail_s` (900 s), those whose first impact came later than 900 s or who had none after being watched more than 900 s. A newbie with no impact who was watched 900 s or less is unresolved for the tail and left out of its denominator. Exactly 10% passes; an impact at exactly 900 s is not in the tail. The detail line reads like "12.0% over 900 s (3/25), needs <= 10%" (one decimal, so 10.4% never shows as the 10% limit); the JSON has `A2.tail` (`limit_s`, `over`, `judged`, `share`), per persona kind too. The report shows the first-impact kind breakdown, overall and per persona kind.

## Local run queue (NX-381)

Spec: Q-OPS-14. Long runs go to the owner's PC (WSL2 Ubuntu). A cloud session opens a GitHub issue labelled `harness-run`; an hourly timer runs `tools/balance/harness_queue.py run-once`, which runs each eligible issue with `balance.py` at the requested commit and comments `report.md` back, swapping the label to `harness-done` (or `harness-failed`, with the exit code and the last 40 log lines). The file is `harness_queue.py`, not `queue.py`, because a `queue.py` beside `balance.py` would shadow the standard library's `queue`. Config: `queue.yaml` (every key is commented). Tests: `services/sim/tests/tools/test_balance_queue.py`.

An issue is eligible when it is open, carries the `harness-run` label and was opened by a login in `trusted_authors`. Anyone else's issue is ignored without a comment. So when an issue sits unpicked past the next tick, check its opener against `trusted_authors` before suspecting the PC or the network (docs/agentic/LESSONS.md L-2). **Token check and late posting (NX-409, L-12).** Before a long run starts the queue proves the `gh` token can write to the issue with `gh issue edit <n> --add-label harness-run -R <repo>`: it adds the label the issue already has, so no label changes and no comment is left, yet it is a real write that needs Issues read and write (a read-only or unapproved token fails it; that the repeat add is a no-op is **[UNVERIFIED]** against live `gh`). If it fails, the queue logs one fixed line (never the token or issue text), leaves the labels as they were and does not start the run; once the token is fixed (organization approval under Settings → Personal access tokens → Pending requests, and Issues read and write on this repository) the next tick picks the issue up. When a run finishes, the queue writes a `finished` marker holding the size of `report.md` in `results_dir/<issue>-<sha8>/`, then posts the report and swaps the label to `harness-done`. If the post or the swap fails, the report stays on disk, the issue stays `harness-running` and the run is not failed. At the start of the next tick, a `harness-running` issue whose directory has a `finished` marker matching the report size gets the report posted (once; a `posted` marker prevents a second comment) and is marked `harness-done`; a stale issue without one, including a partial `report.md`, is resumed (next paragraph) or, when it cannot be, marked `harness-failed`. **Resume after a kill (NX-433).** `balance.py --resume` keeps every `runs/<profile>-s<seed>.json` that parses, names the same profile, seed and hours, carries the current config hash and has the keys the report reads, runs all others again (missing, half-written, another config, or a harness-error stand-in) and builds the report from all of them; run files are written to a `.tmp` name and renamed, so a kill leaves no half file. Apart from the wall-clock fields (`timing`, `workers`, each run's `wall_s` and `ticks_per_s`) the report equals an uninterrupted job's (test). The queue records the validated request in `results_dir/<issue>.request` at start. A stale `harness-running` issue whose results directory exists, with no `finished` marker, is run again in a fresh worktree with `--resume` at the recorded sha and the recorded request, never the issue body (an edit cannot change a resumed job), and posts one report as usual (`Run finished in X (resumed)`). The time shown covers the last attempt only, and `job_timeout_hours` starts again on each resume, so a job can take up to three times that long in all. The write check before a resume adds the `harness-running` label the issue already has (never `harness-run`, which would make the issue eligible again). The count of resumes is in `results_dir/<issue>.resumes`; after `MAX_RESUMES` = 2 the next stale tick marks the job failed, so a job that keeps crashing cannot loop. A resume is the same run, not a new request: the one-run-per-sha refusal below fires only for a `harness-run` issue, and still refuses it. A job killed before `balance.py` made its results directory, or with no readable request file, is failed as before. A first attempt that began on a commit older than NX-433 has no `--resume`: `balance.py` at 4df1f92 exits 2 with `unrecognized arguments: --resume` (QA, run by hand), so its resume is marked `harness-failed`. **The sha that ran (NX-438, L-30).** The queue records the sha at pickup and uses only that one. It prepends `Sha that ran (recorded by the queue at start): <sha>` to `report.md` and prints the same sha in the result comment. When the result is posted (also in a late post by recovery), the queue re-reads the issue body, and if its sha differs it adds `Body sha X was edited after queueing; this run used Y.` (an unreadable body, or one with no valid sha or two `sha:` lines, is flagged the same way). It flags only; it does not refuse. Failure comments carry no such note. Recovery takes the sha from `results_dir/<issue>.running`, written when the run starts and removed when the issue is posted or failed, not from the issue body, so an edited issue cannot redirect it (a missing or non-40-hex file means failed). One crash window is accepted: a crash between the comment and the `posted` marker can post the report twice. One run per issue and SHA: a request for a SHA the issue already ran is refused with a comment (its results directory exists), so recovery can never take an earlier attempt's report for a new one; open a new issue to run it again. The labels need triage rights, so they are the first gate. The request is parsed from the first ```` ```harness ```` block with strict `key: value` lines; an unknown key, a duplicate or a bad value is refused with a comment that names keys only, never the value. Issue text never reaches a shell. The SHA must be reachable from `origin/develop` (`git merge-base --is-ancestor` after a fetch). The run happens in a throwaway `git worktree` (`uv sync --frozen`, then `balance.py`), removed afterwards. A lock file stops two ticks overlapping; a second instance logs and exits 0.

**Overlapping jobs (NX-442, Q-DEV-33).** One tick runs several jobs at once on one worker budget, `max_workers` (12). Each job keeps its own worktree (`wt-<issue>-<sha8>`), sha, results directory, log, report, labels and state files, exactly as a job running alone; recovery and resume handle each issue on its own. Recovery works in two passes: first it posts every finished report and fails every stale issue that cannot resume, then it starts the resumes, each as its own job within the budget (a second resume may wait for the first one's tail), so a resume waiting for workers holds up no post or failure. An issue resumed in this tick is never picked again as a new request, even if someone adds `harness-run` to it meanwhile. A running job holds min(its workers, its runs left) of the budget, where runs left is profiles × seeds minus the `runs/*.json` result files in its results directory (no IPC; a `.tmp` file does not count). While a job runs, the next eligible issue (asking for w workers) starts once min(w, `min_overlap_workers` (6)) budget workers are free, with min(w, the free count) as its `--workers`; with nothing running it gets what it asked for. Issues start oldest first: one that does not fit yet holds back the younger ones (no overtaking, so a big request cannot starve). `min_overlap_workers` must be an integer from 1 to `max_workers`, or the tick stops with an error. That is the rule for a **legacy** sha, one whose `balance.py` has no `--slot-dir` (see "Elastic workers" below): it keeps that count to the end, because its pool is never resized, so a job started beside another may run on fewer workers than requested (its report's `workers` says how many). A job asking for fewer than 12 leaves the rest of the budget free, so the next issue can start beside it at once. The tick holds the lock for as long as any of its jobs runs and does all picking itself: each job is a thread of the tick waiting on its own `balance.py` subprocess, and every few minutes (`POLL_S`, 300 s) or when a job ends the tick recounts result files and lists `harness-run` issues again, so an issue queued during a run can still start beside it. An issue that was tried but not started (a failed `git fetch` or write check) is tried again once `POLL_S` passes, within the same tick. A job that dies (in tests: a stand-in for a kill) is logged and left `harness-running` for the next tick's recovery; the other jobs run to the end and new ones may still start; the error is raised (the tick exits non-zero) and the lock is freed only after every job of the tick has ended. Worktree add, remove, prune and `merge-base` on the shared clone run one at a time; `git fetch` does not take that lock. A long overlapping tick keeps running the queue code it started with (`queue-tick.sh` resets the clone only when a tick starts), so a fix to the queue lands only once all of that tick's jobs have ended. `job_timeout_hours` applies to each job on its own, and a job started on fewer workers takes longer, so it gets closer to that limit. On a resume a result file that `balance.py` will run again (another config, a harness-error stand-in) counts as done until replaced, so the free count is too high by that many and the jobs together can briefly use that many workers over the budget.

**Elastic workers (NX-460).** The budget is `max_workers` slot files, `work_dir/slots/slot-00 …`, which the queue reconciles at the start of each tick (holding the lock): missing ones are created, extra ones removed, and `wait-*` files nobody holds a lock on are deleted. The queue runs `balance.py` from the requested sha's worktree, so an old sha does not know `--slot-dir`. For each job it reads `tools/balance/balance.py` at that sha with `git show` (argv list, no checkout, the text only searched for `--slot-dir`). An **elastic** job gets `--slot-dir <work_dir>/slots --slot-key <issue number> --workers <requested>`; the queue holds nothing for it, its workers take slots themselves, so it widens the moment another job's slots free up. A **legacy** job gets today's behaviour: the queue holds slots on its behalf, min(workers, free) at the start and down to min(workers, runs left) as result files appear, and the `min_overlap_workers` rule applies to it only. The start rule counts demand, not locks: a running job demands min(its workers, its runs left) and free budget is `max_workers` minus the sum, so a job that has not taken a slot yet already counts. The next eligible issue (oldest first, unchanged) starts when at least 1 is free (an elastic one, with the workers it asked for; it widens as older jobs' tails free slots) or when its `min_overlap_workers` rule holds (a legacy one, with min(w, free) workers). For a legacy job the queue takes as many slot locks as it can without blocking (elastic workers may still hold some), tops them up to min(workers, runs left) on each recount and releases them as runs finish. Nothing from the issue body reaches argv beyond the validated fields: the slot key is the integer issue number. A resumed job takes slots like any other. Caveats: `job_timeout_hours` counts a job's slot waiting; and if the queue process is force-killed, orphaned `balance.py` workers keep their slot and wait locks until their current runs end, which can delay younger elastic jobs (bounded by one run; no worse in kind than an orphan running unthrottled before). The queue reads the sha's `balance.py` only after the sha passed the `origin/develop` check, with `git cat-file -s` (over 1 MiB: legacy) then `git cat-file blob` as bytes; any failure counts the sha as legacy for that call and is retried later, never cached. `--dry-run` creates no slot files.

**Trust.** The `harness-run` label gate is only as strong as the list of people with triage rights. A collaborator could edit a trusted author's issue; the damage is still bounded to SHAs on `develop`, profiles that exist in `profiles.yaml` and capped numbers (`max_*`, `job_timeout_hours` in `queue.yaml`). GitHub login reuse (a deleted account's name re-registered) is a residual risk, so keep `trusted_authors` current. A job past `job_timeout_hours` is killed with its child processes and marked `harness-failed`; an issue left `harness-running` by a crash or reboot is resumed at the start of the next tick (at most twice), then marked failed.

**Closing a result (owner rule, 2026-10-26).** The queue never closes an issue: it can't know a result was read. The lead session closes a `harness-done` issue once its result is analysed, within a day or two, with a comment linking where the analysis went (an entertainment review in `docs/review/`, a PR, or a tracker row). An issue still open after that means the result has not been read yet.

### Requesting a run

Never edit the `sha` of a queued request: the run may still go at the sha first read (L-30); close it and open a new issue. Before writing why a run is needed, check the values it would change at that `sha` (`balance/default.yaml` plus your `set`): a request that sets a key to its shipped value repeats an earlier run (L-28).

Anything stock-driven (upkeep, starvation, hauling) needs at least 24 game hours per run before it sets a value: a forward airbase's opening stock lasts the first hours, so a 2-hour upkeep probe measured 0.15% raid grounding where the 24-hour run (K3, #424) measured 15.9% (L-34).

Open an issue with the `harness-run` label (you need triage rights, and be a trusted author). Body:

````
```harness
sha: 0123456789abcdef0123456789abcdef01234567
profiles: prime-50, evening-150
seeds: 5
hours: 72
workers: 4
set: tasking.strike_idle_targets_max=0
```
````

`sha` is 40 lowercase hex characters on `develop`; `profiles` are names from `profiles.yaml`; `seeds` is 1 to `max_seeds`; `hours` is above 0 and at most `max_hours`; `workers` is optional (1 to `max_workers`, default from `queue.yaml`; `max_workers` is 12 and the default `workers` stays 2: ask for 12 (the owner barely uses the PC by day or night, 2026-10-26), about 20% less wall time per job with each run about 25% slower (issue #278); 12 matches the i7-8700's 12 threads; workers beyond `profiles × seeds` sit idle, so give a 12-worker job at least 12 runs, e.g. 6 seeds per profile for two profiles; measured on #385: 6 runs kept 6 of 12 workers busy, about 44% CPU); `set` is optional: up to `max_overrides` comma-separated `key=value` balance overrides (see `--set`; the key must exist at that `sha`, which must also have `--set`, and a `true`/`false` value needs NX-412 part 5a there), echoed in the result comment. The queue accepts only a dotted key (first segment lower case, later ones may be an upper-case side or unit kind, e.g. `economy.upkeep.STRIKE_FIGHTER`) and a bounded number or `true`/`false`; anything else refuses the whole request naming the key `set` only; balance.py then checks the value against the key's type. For a sweep, open one issue per value (0, 1, 2, 4). Wait for the next hourly tick.
